## Intent

**Problem:** Customer owner access can trust an unverified trim, persisted integer/date inputs can pass validation and fail or shift during storage, and a transmission-fluid log can commit against a concurrently replaced transmission branch. These gaps can expose exact-fit parts or maintenance evidence that does not belong to the saved vehicle state.

**Approach:** Make reservation provenance, request parsing, and transmission maintenance writes fail closed at the server boundary, with guarded transactional writes and executable handler tests.

## Boundaries & Constraints

**Always:** Founder access remains based on the exact supported garage vehicle. Customer ready/claimed access requires verified year/make/model and a verified non-null trim before any owner payload, claim, or exact-fit part is exposed. Prisma `Int` inputs are finite bounded integers. Maintenance dates are either exact `YYYY-MM-DD` values or ISO datetimes with an explicit offset, never normalized `24:00` or timezone-dependent strings. A next deadline must be strictly after the completed service boundary. Transmission maintenance must invalidate a stale concurrent transmission picker write or reject itself; both must never commit against different revisions.

**Ask First:** Adding a human trim-verification override, changing eligibility for reservations without a trim, changing the 7/30-day policy, schema/DDL changes, or deploying.

**Never:** Treat twin assignment alone as trim verification; accept malformed JSON as a server error; trust JavaScript date normalization; rely on transaction isolation without a vehicle revision write/guard; mutate production, apply DDL, commit, push, or deploy during this slice.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|---------------|---------------------------|----------------|
| Customer trim provenance | Ready/claimed reservation with non-null `trim` and false/missing `trimVerified` | No claim or owner payload; no history or exact-fit parts loaded | Deterministic eligibility rejection |
| Valid request | Integer mileage/year and exact date-only or offset datetime | Stored without calendar or timezone drift | Normal success response |
| Invalid request | Fractional/out-of-range integer, malformed JSON, impossible/ambiguous date, or equal/backward next deadline | No write | HTTP 400 with validation response |
| Concurrent branch change | Transmission service and picker PATCH use the same starting vehicle revision | At most one branch-changing outcome succeeds; no stale service record | HTTP 409 for the loser |

**Acceptance Criteria:**
- Given any customer reservation with unverified exact-fit provenance, when ready, claim, or owner access is evaluated, then it fails before maintenance history or parts cross the boundary.
- Given a valid integer/date request, when the handler persists it, then stored values represent the same mileage and instant/calendar date supplied by the caller.
- Given concurrent transmission selection and transmission-service logging, when both start from one revision, then one conflicts and no record is assigned to a branch different from the final saved vehicle.
- Given malformed client input, when either handler runs, then it returns 400 and performs no database write.

## Design Notes

For a transmission-service write, a serializable read alone is insufficient because the transaction may legally serialize before a later picker update. The service transaction must perform a compare-and-swap revision write (or equivalent row-version mutation) before record creation so the picker’s `expectedUpdatedAt` becomes stale; if the picker wins first, the service guard must fail or normalize from the new locked revision.
